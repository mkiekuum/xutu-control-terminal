# v2.5 最近十批历史

主界面有“撤销、重做、历史记录”。一份含写操作的 JSON 是一个批次，不按步骤计数；执行前自动保存受影响对象的完整 before，结束后回读 after、真实版本、结果与可恢复能力。execution.backup:false 不能禁用这套保护。旧的 snapshot:* 手动快照仍保留，存储互不覆盖。

只读、预览、全失败、只有版本变化而没有实际业务改变的批次不占十条。仅确认实际改变的记录进入环形历史，保留最近十条；淘汰不删除 job 去重记录。新修改结束旧的重做分支。IndexedDB 数据库 xutu-private-v25、schema 1；按固定网站 origin 与实际 actor 分隔，同账号其他标签可查看，同浏览器配置重启后保留。记录中包含业务快照，只在本机。

## 恢复规则

- 撤销先比较当前版本和字段与预期 after；重做比较恢复后的预期状态。有人改过日期、人员、工期或审核/分组时不覆盖，返回 UNDO_CONFLICT / REDO_CONFLICT 及字段差异。
- 普通计划恢复复用已核实的 /import；新建的撤销使用 /trash，重做使用 /undelete，保留原 ID。删除到垃圾桶可用 /undelete 逆向恢复。没有永久删除承诺。
- 恢复请求使用新的独立请求/操作 ID，版本取真实回读值，不猜加一，不重放旧请求。
- 三个计划一批只占一条，但逐个写入、逐个回读；不是事务。部分恢复显示 partial_undo / partial_redo，成功目标保留、列出剩余目标。再点同方向恢复只尝试尚未成功的目标；有并发差异仍停止，不擅自接受新状态。
- 审核、权限/项目组、工作任务表及任意脚本没有已验证的完整逆向契约。已发生这些改变的批次标为 unsupported，不能跨过它恢复旧点。创建成功而分组被明确拒绝，仍能恢复已确认的创建部分；分组结果未知则先停止核对。
- 任意 script.execute 的副作用 not_guaranteed，不能把它说成已自动全部捕获。服务器最终权限、审核条件和编号冲突始终生效。

## 历史对比

选择记录的 before/after；可对比网站当前内容或另一条记录。显示名称、编号、计划负责人、日期、节点/工作字段、估时、执行人、完成日期、基线和坐标差异；审核、项目组另列。先对比当前状态，界面才启用“恢复选中状态”。恢复路径遇到不可逆记录则停止，不只把整份 JSON 文本称作业务差异。两批没有共同记录的对象标为无法比较，不将缺少快照当成计划不存在。

## 失败与容量

执行前存储失败阻止写入；写后保存失败不会声称撤销可用。中断、超时或无法确认的写入保留 pending，阻止下一次写入/恢复，不能盲目重试。先核对网站，再点“已核对，回读后保留网站现状”：只读当前状态，关闭恢复缺口，受影响旧记录标不可恢复；不重放未知写入，也不清除原请求去重记录。

历史面板显示近似占用 KB；批次上限十条并裁剪无关联 expected 状态。浏览器配额不足会明确失败，不自动删除去重记录。清除扩展存储、卸载、不同浏览器配置或换电脑不保证保留历史；不要为解决未知结果而清库。旧 v2.4 日志无法证明账号归属时只阻止重复执行，不泄露旧结果。

## 命令

history.list、history.diff、history.undo、history.redo、history.restorePoint、history.resolvePending 都是扩展自身接口；history.restore 仍是此前观察到的服务器版本恢复契约，不能与本地 history.restorePoint 混淆。历史恢复与普通业务写入不能混在同一 JSON 批次。

验证：内存模拟与 fake-indexeddb 覆盖 11→10、撤销三次/重做两次、新分支、三个计划部分恢复、重启、隔离、并发、配额失败、结果未知；这些不是公司真实服务器的恢复验收。
