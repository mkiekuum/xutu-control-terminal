# 局部修改与可靠性契约（2.4）

## 给使用者

写需求 → 复制给任意 AI → 回答本次必要的问题 → 粘贴完整 JSON → 查看输入框下的改动摘要 → 执行 → 查看结果。不增加每次确认弹窗。只求建议时，AI 应只给建议。没有自动连接外部 AI 服务。

只改名称不等于改负责人、工期或依赖；整理编号不等于强制串行；简化表达不等于删除工作或合并任务。摘要来自指令列明的操作，不证明 AI 正确理解了业务。需核对摘要是否符合自己的需求。

更多→表达与修改偏好是可选入口：用途、详细程度、名称表达、结构建议和编号偏好。本次选择只随提示词复制；只有点击“记住这些选择”才保存。可修改后再次记住，或重置为中性默认。长期偏好按网站真实登录 actor、新建/管理场景分别隔离，只在本浏览器保存，不自动迁移到同事或新电脑。保存时会重新验证登录身份；旧账号页面不能写入新账号偏好。偏好不是修改业务的额外授权。

网站硬性规则包括节点/连线模型、有效无环图、估时/日期格式、零工期虚线、权限和版本保护。评分的长短工期、串行、合并等是质量建议，不能为提分改变事实；名称风格、是否使用“学习”、是否连续编号属于个人选择。

## 命令参数

新命令是插件本地变换，使用已有 `/api/plans/:id/import`，并非新增服务端接口。首次操作必须指定读取到的 `target.version`。从最新快照复制完整数据，再只修改列明字段；`planNumber`、`planOwner`、未改内容/人员/日期/估时/依赖/进度、日期基线和布局保持。请求附真实 `baseRevision` 和稳定 `operation`；写后比对完整关键字段，包括 positions/baseline。服务器若规范化导致不匹配，报告未确认，不报成功。

| 操作 | 含义 | 参数 |
| --- | --- | --- |
| node.update | 单节点修改 | id、set（name/content/owner） |
| node.batchUpdate | 一次提交多个节点的局部字段 | updates 数组，每项 id、set（name/content/owner），不得重复或空修改 |
| node.reorder | 仅改变显示排列 | ids 为全部节点的排列；不会重编号 |
| node.renumber | 按明确映射改 ID | mapping 数组，每项 from/to；可部分映射、可交换；新 ID 不得冲突 |
| edge.* | 业务依赖或工作修改 | 使用已存在的端点/估时/执行人参数，不能由连续编号推导新边 |

node.renumber 同步节点 ID、连线 from/to、positions 键（包括位置和固定标记），保留工作与用时。名称/内容中的 `[[node:旧编号]]` 被视为明确引用同步；这是插件约定的可见文本标记，不是网站新增字段。普通数字不会自动替换。自然语言引用需在 `references` 中指定 `{nodeId,field:"name"或"content",before,after}`；精确匹配整段原文，否则拒绝整个本地变换。references 的 nodeId 使用旧 ID。不要同时对同一文本使用自动标记和不同的 before，否则校验会拒绝，先明确需要的文本。

网站已观察的 baseline 仅含 confirmedAt/forecastDate 日期元数据，保持原值。若出现未核实的额外基线结构，新命令拒绝重编号，以免破坏未知引用。未承诺识别所有自然语言、附件或其他网站扩展字段中的隐含引用。

## 可复制示例

以下都是占位示例：先读取真实计划，替换目标 ID、版本和节点 ID。不能对生产计划直接重放示例。首次修改只改名称时不需要准备整份计划。

```json
{
  "protocol": "xutu.command/v1",
  "requestId": "unique-rename-job",
  "steps": [{
    "id": "rename",
    "op": "node.batchUpdate",
    "target": {"id": "REPLACE_WITH_PLAN_ID", "version": 27},
    "params": {"updates": [
      {"id": "10", "set": {"name": "需求确认"}},
      {"id": "20", "set": {"name": "验收完成"}}
    ]}
  }]
}
```

重编号使用 `node.renumber`，例如 `params: {"mapping":[{"from":"10","to":"1"},{"from":"20","to":"2"}]}`。先展示 10→1、20→2 对应关系；它不会增加 1→2 的新业务依赖。

同一信封后续修改仍针对这个计划时，可写 `target: {"id":"REPLACE_WITH_PLAN_ID","versionFrom":"rename"}`。仅允许引用本次已成功并且服务端回读确认的步骤，不允许同时写 version，也不允许跨计划。执行器填入真实 afterVersion，不猜加一。若前一步没有确认版本，则不执行后一步。validate/preview 不产生已写入版本，不能作为 versionFrom 来源；预览多步应分别基于真实快照，不能虚构模拟版本。

## 冲突、重试与部分成功

1. 写前读取最新内容和真实版本；提供的旧版本不一致就拒写。
2. 读后发生并发修改，服务器仍可拒绝写入；插件不移除版本检查。
3. 冲突后由错误处理器独立 GET 最新计划，结果写入 diagnostic，不受后续步骤 dependsOn 或 continueOnError 影响。读取失败也单独记录，绝不说已获取最新内容。
4. 有执行前快照时列出可确认差异；只有过期版本号而没有旧全文时，只能列出拟改字段、最新值和拟改值，不能假称知道全部冲突字段。保留服务器最新值，让实际使用者在 AI 对话中选择保留或明确新修改。本版没有自动合并。
5. 兼容旧 onConflict 枚举，但 refresh-retry / overwrite-if-authorized 不再触发覆盖重试。新指令使用 fail 或省略。
6. 网络超时或写后回读失败标记 outcome=unconfirmed，并尝试只读查询；看到最新内容不代表能证明那次写入是否执行。不得自动再写。明确权限/参数拒绝标记 not_executed。
7. 同一 requestId 与相同信封返回已保存结果；不同内容复用同 ID 拒绝。输入 ID、执行、结果与日志保持一致。输入没有 ID 时界面按规范化 JSON 生成稳定 ID；重新打开弹窗不会自动把同一作业换号重写。新意图才使用新的唯一 ID。
8. 本机中断只留下开始记录时拒绝重放；先查 system.status 和用新的只读请求读取计划。清空扩展存储会失去本机防重日志；不要清日志后重放未知写入。跨浏览器不共享锁，不能保证跨安装幂等。

单次批量操作只有一次受版本保护的 POST；这是缩小并发窗口，不是已证明的数据库原子事务。多步骤、跨计划修改可能部分成功：已成功的步骤保留，不自动恢复旧快照；失败和未执行步骤分别报告。服务器审核状态若因业务变化依法变化，以服务器为准；插件不直接覆盖审核字段。

合并/拆分仍检查独立验收、外部依赖和完成状态。结果 changes.durationComparison 提供本地 CPM 期望工期前后比较，不是完整资源日历或网站预计完成日；真实网站工期及评分应在更新后重新读取。真实技术依赖、资源串行、AI额外依赖须分开核对，同人需要全程投入的工作不能无依据并行。

## 结果和隐私

格式通过、预览、服务端回读确认、部分成功、未执行、结果尚未确认分别表达。主要界面使用普通说明，技术码与细节留在可展开结果中；结果可复制给用户选择的 AI，可能含计划内容，不能公开上传 GitHub。基础兼容检查不是全功能正常或写权限认证。

完整 Schema 见 schemas/operation.schema.json、command.schema.json、result.schema.json；本轮测试及真实验证边界见 V2.5_TEST_REPORT.md。新增写入操作尚未在真实网站验证，安装重载需用户在浏览器允许的流程完成。

2.5自动批次快照不受backup:false控制；同批后续无显式版本的操作也使用前步真实回读版本。快照与首写之间有并发修改时拒绝，不能把旧日期保存在可撤销记录后再覆盖它。见V2.5_UNDO_HISTORY.md。
