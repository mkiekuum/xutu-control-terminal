# v2.5 需求问卷

主界面保留需求框和 JSON 框，使用帮助直接显示在主要流程下方，不在“更多”里。默认“新建”；“管理”包括新增、删除、合并、拆分、编号、人员、日期和进度等已支持操作。

1. 写需求并点“复制 AI 提示词”。新建或复杂调整会打开问卷，同时可复制核对资料向 AI 讨论。
2. 在问卷填写答复，点击“保存答复”。日期没决定时勾选“明确暂不设置”；空白输入不是同意。表达与修改习惯也在问卷中。
3. 再复制提示词给 AI；它会收到已答事实、当前真实上下文和参数契约，不应重复问已明确的信息。
4. AI 应在聊天正文给一个完整 JSON 代码块，不交付文件链接。粘贴后查看名称、日期、分工与三点估时，点击“已核实这份方案”，再执行。
5. 仅改标题、名称或编号等简单操作不强制整份业务问卷，也没有每次确认弹窗。用户只要建议时，不生成写入指令。

## 首轮与补问

复杂新建或重大调整首轮 3–6 题：名称/编号，开工/硬截止，真实项目组，交付/优先级/验收，人员/设备/工期，表达偏好。已提供的日期、无硬截止、真实项目组等直接沿用；通常剩余三个业务问题。简单管理只提供可选表达问题，不追问整份计划的人员和日期。后续只补缺项。

结构复杂度的执行门禁包括全量替换、大量新节点、多条结构/工作修改；单纯批量改名、重编号、显示排序不因数量多就强制业务问卷。自然语言中出现“老板、复杂、重构、多团队、20节点、并行”等会触发复杂任务预检。关键词检测不是自然语言理解保证；外部 AI 仍须核实具体业务含义。

## 真实门禁

台账在本机 IndexedDB，绑定网站 origin、实际 actor、标签、用途、管理目标及版本。JSON 的顶层 intakeId 只是引用，不能添加 intakeComplete 等字段伪造完成。复杂任务和 plan.create 在任何写入前核对台账；首轮未答、项目组已不可见、账号/目标变化、日期与答复不符、具体提案未确认，都停止写入。preview/validate 不执行写入，也不把问卷标成已答。

人员/估时确认绑定整份 steps 的哈希。确认后 JSON 改动需要重新核对；重复执行同一请求不会换号重写。确认动作仅在插件 UI 提供，AI 不能通过 JSON 自行批准提案。真实工作未填执行人时，必须补分工，或明确“暂不分配/草稿”；模拟、练习、演示可用角色说明，不强加名称前缀。

## 表达习惯

默认中性、易懂，不继承作者的个人习惯。问卷中可填写简洁/详细、汇报/执行、保留名称、编号和调整范围。只勾选“记住表达习惯”才长期保存；按 actor 和新建/管理用途隔离。之后仍可编辑，也可在问卷点“重置表达习惯”。旧版偏好数据保留在本机，但不会未经核实自动套用到新问卷。

## JSON 方式

intake.inspect 建立或读取台账；intake.answer 保存已获得的用户答复；intake.status 读取状态。JSON 执行结果会同步回问卷 UI。示例 46–50 使用示意 ID，必须替换为本机实际返回值；不能复制他人 intakeId。跨计划的复杂重构请按目标分别建立问卷，简单跨计划局部编辑仍可作为一个批次。

没有登录时可先向 AI 讨论需求，但不能确认实际账号、组或执行正式写入。问卷不证明业务方案正确，服务器仍最终决定权限。
